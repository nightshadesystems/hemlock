# Porting Hemlock to the Edgecore AS4610-54T

Phase 0 spec. Everything below is a proposal for review; nothing in
`src/`, `platforms/` or `build/` changes until it is accepted.

The AS4610-54T (ONIE `arm-accton-as4610-54-r0`) is 48x1G copper
(BCM54282 octal PHYs) + 4x10G SFP+ (BCM84758) + 2x20G QSFP+ stacking,
driven by a Broadcom BCM56340 (Helix4) whose **host CPU is the on-die
iProc dual-core Cortex-A9**. 2 GB DDR3, 8 MB SPI-NOR (U-Boot + ONIE),
8 GB NAND. Management is the iProc GMAC.

The porting guide's happy path — one directory under `platforms/`, zero
Rust changes — does not reach this board. Two facts break it, and both
were re-verified against primary sources rather than taken on trust.

## Blocker 1 — the host CPU is ARM, and the pipeline is x86_64-only

There is no PCIe: the CMIC is CMICd on the SoC bus
(`iproc_cmicd@48000000` in the device tree). Boot is U-Boot + a FIT
image, not GRUB. Every stage of the build pipeline assumes x86_64:

| Stage | Where it is nailed to x86_64 |
|---|---|
| `build/mkimage.sh` | `debootstrap trixie` (host arch), GRUB assets from `build/rootfs/grub.cfg.in`, installer built for `x86_64-unknown-linux-musl` |
| `build/build-bde.sh` | `systems/linux/user/x86-smp_generic_64-2_6`, `arch/x86` header links |
| `hemlock-installer` | GPT + BIOS-boot + ESP + `grub-install --target=i386-pc`; `machine.rs` defaults `onie_arch` to `x86_64` |
| `build/verify-image.sh` | requires `boot/grub.cfg`, `boot/vmlinuz`, `boot/initrd.img` |
| `hemlock-sai/build.rs` | bindgen `--target=x86_64-unknown-linux-gnu` (deliberate, and harmless here — the OpenBCM backend uses no bindgen) |

Also relevant: `hemlock_platform::sysinit::broadcom_asic_present()`
probes PCI vendor `0x14e4`. On this board **it returns false with the
ASIC present**, so `--auto-mock` would silently mock a real switch —
exactly the failure mode that check exists to prevent. Fixing it is not
optional.

## Blocker 2 — no armhf SAI exists

Verified, not assumed:

- SONiC's `platform/broadcom/sai.mk` (202305, the branch the E1031 pin
  comes from, and master) hardcodes
  `libsaibcm_$(LIBSAIBCM_XGS_VERSION)_amd64.deb`. There is no arch
  variable.
- Direct probe of the SONiC package server:
  `.../SAI_8.4.0_GA/8.4.50.0/xgs/libsaibcm_8.4.50.0_{armhf,arm64}.deb`
  → **404**; `_amd64.deb` → **200**.
- `device/accton/` in sonic-buildimage has no `as4610` directory at all
  (only `as4630`), on master or 202305. SONiC never supported this box.

So Hemlock's "SAI only, never the raw SDK" principle cannot be
satisfied here with a vendor blob. The only datapath available for
Helix4-on-ARM is Broadcom's source-available OpenBCM SDK. Verified
present: `OpenBCM/sdk-6.5.16/src/soc/mcm/bcm56340_a0.c`,
`sdk-6.5.16/src/soc/esw/helix4.c`, and the
`sdk-6.5.16/systems/linux/user/iproc-4_4` build target.

> Correction to the brief: OpenBCM has **no** `sdk-6.5.16` branch or
> tag. The repo has a single `master` branch with one directory per SDK
> release (`sdk-6.5.16` … `sdk-6.5.27`). The fetch recipe is a sparse
> checkout of that path at a pinned `master` commit.

## Decision — a second backend behind the existing `SaiBackend` seam

`docs/porting-guide.md` already names the extension point ("a new SAI
object family → `SaiBackend` trait + mock + vendor impl"). We use it one
level lower: a **second concrete backend**, selected per platform by the
manifest. `hemlock-syncd`, `-orch`, `-mgmtd`, `-webd` and `hemlockctl`
stay untouched — they only ever see the trait.

### Alternatives considered

**A. In-process bindgen against `libbcm.a`.** *Rejected.* It drags an
enormous `-ansi` header set with SDK-specific `#define` soup through
bindgen on every build; it makes `hemlock-syncd`'s link line
platform-specific, so the workspace no longer builds one binary set per
architecture; it forces the SDK's `sal_config` / `sysconf_*` init model
into Rust; and `unsafe_code = deny` would have to relax far beyond
`hemlock-sai`'s FFI modules. Worst, the SDK's build is a recursive make
that wants to own its tree — reproducing it inside `cargo` is a
permanent tax.

**B. Write a SAI implementation on top of OpenBCM, in C**, so the
existing `real-sai` backend works unchanged. *Rejected.* Largest
possible amount of C for the smallest gain: SAI 1.11 is roughly forty
object types and thousands of attributes, and we would only ever
exercise the fraction the `SaiBackend` trait uses. We would own a SAI
implementation's correctness — attribute semantics, object-id encoding,
notification threading — forever, in the language we are trying not to
write, to feed an adapter that immediately narrows it back down again.
We need *the trait's* surface, not SAI's.

**C. A thin C shim inside the OpenBCM tree, exposing a small versioned C
ABI that mirrors the `SaiBackend` method set — `libhemlockbcm.so`,
dlopened by a Rust `OpenBcmBackend`.** **Chosen.**

The shim is built by the SDK's own make system — exactly how edgenos
appends `bcmd.c` to `socdiag.c` and relinks `bcm.user`, which is proven
on this board. All OpenBCM headers stay on the C side; Rust never sees
`bcm_*` types. The ABI is *ours*, so it is small, stable and documented
in a file we own — and its surface is precisely the surface we have
already committed to keeping honest, because it is the trait.

Cost, stated plainly: two backends to keep in step, and a C artifact
that cannot be built or tested in CI. The mitigations are the committed
ABI header (which CI *does* compile against) and a stub `.so` the Rust
unit tests dlopen — see Phase 2.

### The ABI contract

`src/hemlock-sai/openbcm-shim/hemlockbcm.h` is **ours** (MIT), committed,
and is the contract. It defines:

```c
#define HEMLOCKBCM_ABI_MAJOR 1
#define HEMLOCKBCM_ABI_MINOR 0

struct hemlockbcm_api {
    size_t   struct_size;            /* sizeof(struct hemlockbcm_api) */
    uint32_t abi_major, abi_minor;
    int (*create_switch)(struct hemlockbcm_switch **out,
                         const struct hemlockbcm_init *);
    int (*ports)(struct hemlockbcm_switch *,
                 struct hemlockbcm_port *, size_t *inout);
    int (*set_port_admin_state)(struct hemlockbcm_switch *,
                                uint32_t port, int up);
    /* ... one slot per SaiBackend method, in trait order ... */
};

/* The only exported symbol. */
const struct hemlockbcm_api *hemlockbcm_get_api(uint32_t want_major);
```

Versioning rule, mirroring the SAI-pin rule already in the architecture
doc:

- **Major** bumps on any incompatible change — a slot's signature or
  semantics change, a slot is removed or reordered. Rust refuses to load
  a shim whose major differs.
- **Minor** bumps when slots are appended. Rust accepts any minor and
  uses `struct_size` to know how much of the vtable is real.
- **A NULL slot is legal** and means "not implemented on this
  platform". `OpenBcmBackend` turns a NULL slot into
  `SaiError::Status` carrying `SAI_STATUS_NOT_IMPLEMENTED`, which
  `SaiError::is_unsupported()` already classifies — so `capabilities()`
  reports the truth and the CLI and web console degrade exactly as they
  do today on a SAI missing a family. Nothing new is invented.

Port identity: `hemlockbcm_port.id` is the **chip logical port number**
(1..48 copper, 50..53 SFP+, 54..55 QSFP+), which is also what the
manifest's `lanes` list carries for this platform (see below). syncd's
existing correlate-by-lane-set join needs no change.

### The principle, restated honestly

`README.md` and `docs/architecture.md` currently say Hemlock drives
Broadcom XGS "exclusively through the vendor's SAI library — never the
raw Broadcom SDK". That sentence stops being true. The replacement:

> SAI is the preferred backend and the default. Where no SAI build
> exists for a platform's CPU architecture, a second backend over the
> source-available OpenBCM SDK is permitted — behind the same
> `SaiBackend` trait, selected by the platform manifest, and never
> visible above `hemlock-sai`.

## Schema additions

All additions are `#[serde(default)]`, so every existing manifest keeps
parsing byte-identically. `platforms/_template/platform.toml` documents
each one.

### 1. Backend selection — `[sai]`

```toml
[sai]
backend = "openbcm"                        # "sai" (default) | "openbcm"
shim_path = "/usr/lib/libhemlockbcm.so.1"  # openbcm only; dlopened by syncd
abi_major = 1                              # openbcm only; refuse a mismatch
config_bcm = "as4610-54.config.bcm"
```

`package`, `version_pin`, `api_headers` and `libsai_path` become
`Option`, **required by lint when `backend = "sai"`** and rejected when
`backend = "openbcm"`. `asic_family` stays `"broadcom-xgs"`;
`asic = "helix4"`. The section keeps its name because it is the
*datapath library* section; renaming it would churn every manifest, the
loader, lint, `mkimage.sh` and the architecture doc for no gain.

### 2. CPU architecture — `[platform]`

```toml
[platform]
cpu_arch = "armhf"    # default "amd64"; drives mkimage/installer/verify
```

Lint cross-checks it against the `onie_machine` prefix (`arm-` with
`armhf`, `x86_64-` with `amd64`) so the two cannot disagree silently.

### 3. Multiple i2c roots — `[hardware.i2c]`

The AS4610's roots are two **SoC** controllers (`i2c0`, `i2c1` in the
device tree), not one PCI SMBus adapter: the CPLD sits at `i2c-0` 0x30
and the pca9548 at `i2c-1` 0x70. Both adapters carry the same driver
name, so `root_adapter` — a single name prefix — cannot express it.

```toml
[[hardware.i2c.root]]
name = "cpld"                        # referenced as bus = "cpld"
adapter = "Broadcom iProc I2C adapter"
instance = 0                         # nth match in bus-number order

[[hardware.i2c.root]]
name = "mux"
adapter = "Broadcom iProc I2C adapter"
instance = 1
```

- `root_adapter = "..."` stays valid, as sugar for one root named
  `root`; declaring both it and a `[[root]]` named `root` is a lint
  error.
- `I2cDevice.bus`, `Psu.bus` and `Transceiver.bus` change from `u32` to
  `BusRef`, so they can name a root directly. Numbers still parse
  (`BusRef::Number`), so the E1031 manifest is unchanged.
- `Sysfs::resolve` gains a root table instead of one `Option<u32>`.
- Lint: root names unique and non-empty; every `BusRef::Named` resolves
  to a declared root. Whether `instance` is in range is a runtime
  concern, not a lint one.

### 4. Fan attributes that are not standard hwmon

ONL's `accton_as4610_fan.c` registers `fan1_speed_rpm` and
`fan1_duty_cycle_percentage`, not `fan1_input` / `pwm1`, and its duty
attribute is **percent**, not 0–255, while Hemlock's sysfs backend
builds `<tach>_input` and writes `percent * 255 / 100`. Two additions
to `[[hardware.thermal.fan]]`, in the style of the `presence_attr` /
`led_attr` escape hatches the schema already has:

```toml
rpm_attr = "fan1_speed_rpm"                  # verbatim attribute name
pwm_attr = "fan_duty_cycle_percentage"       # verbatim attribute name
pwm_max  = 100                               # default 255
```

When absent, behavior is byte-identical to today.

### 5. Default admin state — `[[ports.port]]` / `[[ports.group]]`

```toml
admin_default = "down"   # "up" (default) | "down"
```

The two QSFP+ ports are stacking links; bringing them up by default on
a box wired into someone's rack is a loop waiting to happen. syncd's
startup step 4 ("bring every mapped port to its default admin state")
reads this instead of hardcoding `up`. Roughly ten lines and one test.

## The port table

`lanes` for a `backend = "openbcm"` platform carries the **chip logical
port number**, because that is the stable identity the shim reports —
the same role SONiC's serdes lane numbers play on a SAI platform. This
is documented in the template and enforced by nothing, which is why the
manifest comment must say it loudly.

From `config.bcm` (dumped from the stock ICOS NOS) and `bcmd.c`:

- `pbmp_xport_ge = 0x3fffffffffffe` → logical **1..49** = `ge0..ge48`.
  `ge48` (logical 49) is internal — `port_phy_addr_ge48=0` — and is
  omitted; syncd logs and ignores unmatched ASIC ports.
- `pbmp_xport_xe = 0xfc000000000000` → logical **50..55**:
  `xe0..xe3` = SFP+ (logical 50..53), `xe4..xe5` = QSFP+ stacking
  (54..55). `bcm56340_4x10=1`.
- Copper MDIO addresses run in six banks of eight with gaps
  (`0x1..0x8`, `0xb..0x12`, `0x15..0x1c`, `0x21..0x28`, `0x2b..0x32`,
  `0x35..0x3c`) — one octal PHY per bank, consistent with the BCM54282.
  SFP+ PHYs are `0x40..0x43`.

> Correction to the brief and to edgenos: the `config.bcm` header
> comment says "BCM5464S copper PHY". The 5464 is a *quad* PHY and
> cannot produce banks of eight. edgenos's own
> `docs/packet-flow-as4610-54t.md` says BCM54282, which matches the
> datasheet and the MDIO layout. The `phy_5464S_xe0..3` keys are SFP+
> properties, unrelated to the copper bank. Treating **BCM54282** as
> correct.

Naming stays `Ethernet1..Ethernet52` (plus `Ethernet53`/`54` for the
stacking ports) and `Management1`, per the repo convention.

**Blocking input needed.** The faceplate → `geN` map is scrambled and
pair-swapped, and the brief is right that it must be copied verbatim,
never derived. It is **not in the public edgenos tree**: `bcmd.c`
points at `../PORTMAP.md` and `switchdb` names `as4610-54.portmap`, and
neither file exists in the repository. All that is recorded publicly is
"physical port 1 = ge25, port 2 = ge24, verified on HW". Phase 1 cannot
produce a correct `lanes` list without the full 48-entry map — see open
question 1.

## Cross-build strategy (Phase 4)

**Rust.** `armv7-unknown-linux-gnueabihf` for the daemons (linker
`arm-linux-gnueabihf-gcc`), `armv7-unknown-linux-musleabihf` for the
installer, which must be static because ONIE has no dynamic loader.
Both are tier-2 with std. Preference: link the musl installer with
`rust-lld` so the build needs no third toolchain — to be confirmed in
Phase 4, falling back to a musl cross-gcc if that does not hold.

**Rootfs.** Debian 13 armhf is a real release architecture (the trixie
`Release` file lists `armhf`). `debootstrap --arch=armhf --foreign` +
`qemu-arm-static` + `--second-stage`, then the same package list,
branding, MOTD and initramfs work `mkimage.sh` already does. This needs
root and binfmt, so it stays in `image.yml`'s `full` mode; the
`--dummy-rootfs` path — what CI runs — needs neither.

**Kernel.** The hard part. Upstream Linux has no Helix4 support, only
Hurricane 2 (`arch/arm/boot/dts/broadcom/bcm-hr2.dtsi`,
`ARCH_BCM_HR2`). The public XGS iProc patch set is ONL's
`packages/base/any/kernels/4.14-lts/patches/brcm-iproc-4.14.patch`
(1.1 MB) plus the `armhf-iproc-all` config and the `xgs_iproc_smbus` /
`phy-xgs-iproc` patches. edgenos forward-ported it to 6.1.175, but that
tree is not public. Options, in preference order:

1. Reuse the edgenos 6.1.175 iProc tree if it can be made available
   under a compatible licence (open question 6).
2. Forward-port ONL's 4.14 patch set onto 6.1 LTS ourselves, shipped as
   a `linux-image-<ver>-hemlock-iproc` .deb built out of tree and
   installed into the chroot the way the vendor SAI .deb is today.
3. Pin at 4.19 (ONL has a 4.19-lts tree) and accept an old kernel on
   this platform only. Cheapest, and the least good.

Whichever wins, the DTS is ours: `platforms/accton-as4610-54/dts/`
carries the AS4610 board DTS (RTC disabled — the M41T11's dead battery
makes the 4.19+ RTC core re-arm an expired alarm through a muxed i2c
read every pass, holding `i2c1`'s xfer lock until userspace wedges; NTP
sets the clock, so nothing is lost) plus ONL's `bcm-helix4.dtsi`.

**BDE / KNET.** Not from `saibcm-modules` — that is SONiC's SAI-lineage
tree and there is no SAI here. Build OpenBCM's own GPL
`systems/linux/kernel/modules` for `iproc-4_4` with `BUILD_KNET=1`,
against the image kernel's headers. `build/build-bde.sh` is
x86-specific (`x86-smp_generic_64-2_6`, the `arch/x86` header links), so
Phase 4 parameterizes it by target or adds `build/build-bde-arm.sh`.

**Boot artifacts.** No GRUB. A FIT (`boot/hemlock.itb`) built with
`mkimage -f`: gzipped kernel `Image` (load/entry `0x61008000`), the
board dtb, and the initramfs — the layout edgenos proved on this box.
`mkimage.sh` selects GRUB vs. FIT from `[platform] cpu_arch` and writes
an `arch` marker into the platform overlay.

**Installer.** Hemlock keeps its own self-extracting `.bin` and its own
`hemlock-installer`. edgenos wraps an ONL loader FIT plus a `.swi` with
ONL's python2 `mkshar`; adopting that would import the ONL loader, its
`boot-config` format and a python2 build dependency, and would abandon
Hemlock's squashfs + `/hemlock/persist` contract. Instead
`install.rs` grows an ARM strategy that writes the FIT and
`rootfs.squashfs` to the NAND, places the platform overlay, and sets the
U-Boot environment via `fw_setenv` (which ONIE provides) so
`nos_bootcmd` boots the FIT. `machine.rs` stops defaulting `onie_arch`
to `x86_64`. The NAND layout — raw MTD partitions, UBI volumes, or an
`ubiblock` carrying ext4 — is open question 3, and is the one decision
that genuinely cannot be made off the box.

**CI stays honest.** `verify-image.sh` reads the payload's `arch` marker
and requires `boot/hemlock.itb` instead of `grub.cfg` / `vmlinuz` /
`initrd.img`, so `mkimage.sh accton-as4610-54 --dummy-rootfs` +
`verify-image.sh` still runs on x86 with no toolchain, no blobs and no
root. No CI job needs an ARM toolchain, the OpenBCM tree, or a blob.

## Licensing

- **Nothing from OpenBCM, ONL, or Broadcom PHY firmware is ever
  committed.** `vendor/fetch-vendor.sh accton-as4610-54` fetches the
  OpenBCM `sdk-6.5.16` subtree (sparse, at a pinned commit), the
  `bcm84758_ucode` blob, the OpenMDK Helix4 reference LED program, and
  the ONL/edgenos data files, all under gitignored paths. OpenBCM ships

- ONL kernel modules ported into `platforms/accton-as4610-54/kmod/` are

- `vendor/openbcm-shim/hemlockbcm.c` and
  `src/hemlock-sai/openbcm-shim/hemlockbcm.h` are Hemlock's own code,
  MIT. The shim links against Broadcom-licensed static libs on the

- Hemlock's MIT licence covers Hemlock's own code and nothing else.

## Definition of done, per phase

**Phase 1 — manifest + mock bring-up (data; x86 CI).**
`platforms/accton-as4610-54/` with `platform.toml`, `README.md`
(provenance table) and `boot.env` if needed; the schema and lint
additions above with tests; template updated; the `image.yml` dropdown
and the CI lint job list the platform. Green when `cargo build`, `test`,
`clippy` and `fmt --check` all pass; `hemlockctl platform lint
platforms/accton-as4610-54` reports only vendor-file warnings;
`hemlock-syncd --platform accton-as4610-54 --mock` enumerates
`Ethernet1..52` (plus 53/54) with correct index, speed and media; and a
commit + rollback through mgmtd against that mock succeeds.

**Phase 2 — `OpenBcmBackend` skeleton (x86 CI, no SDK).**
`src/hemlock-sai/src/openbcm.rs` behind an `openbcm` feature;
`openbcm-shim/hemlockbcm.h` committed; `hemlock-sai/build.rs` compiles
`openbcm-shim/hemlockbcm_stub.c` into a cdylib in `OUT_DIR` when the
feature is on and exports its path for the tests. Implemented:
`create_switch`, `ports`, admin/speed/duplex/autoneg/mtu, counters,
`take_events`, `capabilities`; everything else returns unsupported.
`build_backend()` picks the backend from the manifest, and the
ASIC-presence probe learns about the on-die CMIC. Green when CI compiles
and clippies `-p hemlock-sai --features openbcm`; the unit tests dlopen
the stub and round-trip every implemented method; an ABI-major mismatch
and a NULL slot each produce the right error; and
`docs/architecture.md`'s SAI section describes the second backend and
the versioning rule.

**Phase 3 — the C shim (ARM cross container; not CI).** Fetch recipe;
`vendor/openbcm-shim/hemlockbcm.c` plus its SDK-tree build script; the
`as4610` quirks impl (`pre_asic_init`: `iproc_cmicd` unbind, the five
CPLD reset-deassert writes with read-back verification, char devnodes;
`post_asic_init`: LED program plus `led auto on` / `led start`). Green
when the script produces a `libhemlockbcm.so` for `iproc-4_4` with
`BUILD_KNET=1` from a clean checkout, `bcm56340_a0`'s presence in the
pinned commit is recorded in the platform README, and the quirk is
idempotent.

**Phase 4 — armhf image pipeline.** Per-platform arch in `mkimage.sh`;
armhf rootfs; kernel package; cross-built BDE/KNET; cross-built
workspace; FIT assembly; the ARM install strategy; `machine.rs` honoring
`onie_arch=arm`. Green when `mkimage.sh accton-as4610-54
--dummy-rootfs` + `verify-image.sh` pass **on x86 in CI**, and a full
build on a Debian host produces a `.bin` that ONIE accepts.

**Phase 5 — hardware bring-up.** Console → kernel → `ma1` → BDE/KNET →
quirk → `create_switch` → `show interfaces` showing 52 ports with real
link state on a copper port → VLAN + PVID → L3 RIF + static route →
OSPF via FRR. Findings land in the platform README's "Known quirks"
section as they appear, in the style of `docs/e1031-led-bringup.md`.

**Phase 6 — fill out the backend.** FDB, LAG, STP, mirror, storm
control, ACL/policer/CoPP traps, sFlow/samplepacket, QoS — in that
order. Each step is one shim function, one Rust method, a unit test
against the stub, a capability flag flipped, and a hardware check.

## Open questions — I need answers from the box

1. **The faceplate → `geN` map, all 48 entries.** Blocking for Phase 1.
   Not in the public edgenos tree (see above). Either the `PORTMAP.md` /
   `as4610-54.portmap` file, or a sweep on the box: link one port at a
   time and read which logical port carries the link.
2. **Console device and speed.** The DTS aliases `serial0 = &uart1` and
   its commented `bootargs` say `console=ttyS0,115200n8`, which would
   mean no `boot.env` is needed. Confirm from ONIE's `installer.conf`.
3. **NAND layout as ONIE presents it.** `/proc/mtd` and
   `cat /proc/cmdline` from ONIE, plus whether `ubinfo` / `ubiformat`
   and `fw_setenv` exist in that environment. This decides raw-MTD vs.
   UBI vs. `ubiblock` + ext4 as the install target.
4. **U-Boot environment variable names.** `fw_printenv` output from
   ONIE — specifically what `nos_bootcmd` is called on this board, and
   what `onie-nos-mode -c` leaves behind.
5. **Does `ma1` come up as `eth0` under a stock (non-ONL) kernel?**
   `[management] os_device` depends on it; ONL's udev rules are what
   produce `ma1`, and we are not shipping ONL userspace.
6. **Is the edgenos 6.1.175 iProc kernel tree (or its patch series)
   available to reuse?** This is the difference between a week and a
   month on Phase 4.
7. **Device tree vs. manifest for the i2c topology.** The AS4610 DTS
   instantiates the pca9548 and every leaf device in-tree, so child bus
   numbers are kernel-assigned rather than the deterministic
   `child_bus_base` numbering `[hardware.i2c]` assumes. Do we (a) keep
   DT instantiation and let the manifest describe the topology for
   reading only, accepting that bus numbers must be confirmed on
   hardware, or (b) strip the leaf devices from our DTS and let pmon's
   `instantiate_i2c` create them, matching the E1031? I lean (b) for
   uniformity and determinism, but it needs one boot to confirm the
   mux's child buses land where we predict.
8. **PSU/fan sysfs source.** I propose porting ONL's
