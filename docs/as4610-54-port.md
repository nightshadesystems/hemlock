# Porting Hemlock to the Edgecore AS4610-54T

Phase 0 spec, revision 2. A proposal for review; nothing in `src/`,
`platforms/` or `build/` changes until it is accepted. The kernel work
has its own document — [`as4610-kernel-port.md`](as4610-kernel-port.md).

The AS4610-54T (ONIE `arm-accton_as4610_54-r0`) is 48x1G copper
(BCM54282 octal PHYs) + 4x10G SFP+ (BCM84758) + 2x20G QSFP+ stacking,
driven by a BCM56340 (Helix4) whose **host CPU is the on-die iProc
dual-core Cortex-A9**. 2 GB DDR3, 8 MB SPI-NOR (U-Boot + ONIE) and
USB-attached NOS storage. Management is the iProc GMAC (`eth0`).

The porting guide's happy path — one directory under `platforms/`, zero
Rust changes — does not reach this board. Two facts break it, both
verified against primary sources rather than taken on trust.

## Blocker 1 — the host CPU is ARM, and the pipeline is x86_64-only

No PCIe: the CMIC is CMICd on the SoC bus (`iproc_cmicd@48000000`,
`compatible = "brcm,iproc-cmicd"`). Boot is U-Boot + FIT, not GRUB.

| Stage | Where it is nailed to x86_64 |
|---|---|
| `build/mkimage.sh` | `debootstrap trixie` (host arch), GRUB assets, installer for `x86_64-unknown-linux-musl` |
| `build/build-bde.sh` | `systems/linux/user/x86-smp_generic_64-2_6`, `arch/x86` header links |
| `hemlock-installer` | GPT + BIOS-boot + ESP + `grub-install --target=i386-pc`; `machine.rs` defaults `onie_arch` to `x86_64` |
| `build/verify-image.sh` | requires `boot/grub.cfg`, `vmlinuz`, `initrd.img` |

Also: `sysinit::broadcom_asic_present()` probes PCI vendor `0x14e4`, so
here it returns false **with the ASIC present** — `--auto-mock` would
silently mock a real switch, the exact failure that check exists to
prevent.

## Blocker 2 — no armhf SAI exists

- SONiC's `platform/broadcom/sai.mk` (202305 and master) hardcodes
  `libsaibcm_$(LIBSAIBCM_XGS_VERSION)_amd64.deb`; no arch variable.
- Probing the SONiC package server:
  `SAI_8.4.0_GA/8.4.50.0/xgs/libsaibcm_8.4.50.0_{armhf,arm64}.deb` →
  **404**; `_amd64.deb` → **200**.
- `device/accton/` in sonic-buildimage has no `as4610` (only `as4630`).
  SONiC never supported this box.

"SAI only, never the raw SDK" therefore cannot be satisfied here with a
vendor blob. The only datapath for Helix4-on-ARM is Broadcom's
source-available OpenBCM SDK. Verified present in `sdk-6.5.16`:
`src/soc/mcm/bcm56340_a0.c`, `src/soc/esw/helix4.c`, and the
`systems/linux/user/iproc-4_4` target. (`sdk-6.5.16` is a *directory in
`master`*, not a branch or tag; the fetch recipe sparse-checks it out at
a commit pinned in `vendor/openbcm/.openbcm-commit`.)

The SDK README advertises only TD/TH families, but that is a *support*
statement: `make/Make.local.template` says the default build includes
every chip in the release, with partial support opt-in via
`BCM_PTL_SPT`. The Phase 3 gate is behavioral, not a config hunt: **the
`iproc-4_4` target links and `bcm56340_a0` appears in the built chip
table.**

## Decision — a second backend behind the `SaiBackend` seam

The porting guide already names the extension point ("a new SAI object
family → `SaiBackend` trait + mock + vendor impl"). We use it one level
lower: a **second concrete backend**, selected per platform by the
manifest. syncd, orch, mgmtd, webd and hemlockctl stay untouched.

### Alternatives considered

**A. In-process bindgen against `libbcm.a`.** *Rejected.* Drags an
enormous `-ansi` header set through bindgen on every build; makes
syncd's link line platform-specific, so the workspace no longer builds
one binary set per architecture; forces the SDK's `sal_config` /
`sysconf_*` init model into Rust; and `unsafe_code = deny` would relax
far beyond `hemlock-sai`'s FFI modules. Worst, the SDK's recursive make
wants to own its tree — reproducing that inside `cargo` is a permanent
tax.

**B. A SAI implementation over OpenBCM, in C**, so `real-sai` works
unchanged. *Rejected.* The most C for the least gain: SAI 1.11 is ~40
object types and thousands of attributes, of which we exercise a small
fraction, yet we would own that implementation's correctness —
attribute semantics, object-id encoding, notification threading —
forever, in the language we are trying not to write, to feed an adapter
that immediately narrows it back down. We need *the trait's* surface,
not SAI's.

**C. A thin C shim inside the OpenBCM tree exposing a small versioned C
ABI mirroring the `SaiBackend` method set — `libhemlockbcm.so`, dlopened
by a Rust `OpenBcmBackend`.** **Chosen.** Built by the SDK's own make
system, the way edgenos appends `bcmd.c` to `socdiag.c` and relinks
`bcm.user` — proven on this board. OpenBCM headers stay on the C side;
Rust never sees `bcm_*` types. The ABI is ours, so it is small, stable,
and documented in a file we own — and its surface is exactly the surface
we already keep honest, because it is the trait.

Cost, plainly: two backends to keep in step, and a C artifact the
per-push CI cannot build. Mitigations: the committed ABI header (which
CI *does* compile against) and a stub `.so` the unit tests dlopen —
and the on-demand image workflow's `full` mode does build the real
shim (SDK userland + link, cached on the ABI and build scripts).

### The ABI contract

`src/hemlock-sai/openbcm-shim/hemlockbcm.h` is ours (MIT), committed,
and is the contract:

```c
#define HEMLOCKBCM_ABI_MAJOR 1
#define HEMLOCKBCM_ABI_MINOR 0

struct hemlockbcm_api {
    size_t   struct_size;          /* sizeof(struct hemlockbcm_api) */
    uint32_t abi_major, abi_minor;
    int (*create_switch)(struct hemlockbcm_switch **,
                         const struct hemlockbcm_init *);
    int (*ports)(struct hemlockbcm_switch *,
                 struct hemlockbcm_port *, size_t *inout);
    /* ... one slot per SaiBackend method, in trait order ... */
};
const struct hemlockbcm_api *hemlockbcm_get_api(uint32_t want_major);
```

- **Major** bumps on any incompatible change (a slot's signature or
  semantics change, a slot removed or reordered). Rust refuses a
  mismatched major.
- **Minor** bumps when slots are appended; Rust accepts any minor and
  uses `struct_size` to know how much of the vtable is real.
- **A NULL slot is legal**, meaning "not implemented on this platform".
  `OpenBcmBackend` turns it into `SaiError::Status` carrying
  `SAI_STATUS_NOT_IMPLEMENTED`, which `SaiError::is_unsupported()`
  already classifies — so `capabilities()` reports the truth and both
  consoles degrade exactly as on a SAI missing a family. Nothing new is
  invented.

`hemlockbcm_port` carries **both** the chip logical port number and the
SDK name (`"ge25"`), so syncd asserts the manifest's `sdk_names` against
what the chip reports instead of re-deriving anything.

### The principle, restated honestly

`README.md` and `docs/architecture.md` say Hemlock drives Broadcom XGS
"exclusively through the vendor's SAI library — never the raw Broadcom
SDK". That stops being true. The replacement:

> SAI is the preferred backend and the default. Where no SAI build
> exists for a platform's CPU architecture, a second backend over the
> source-available OpenBCM SDK is permitted — behind the same
> `SaiBackend` trait, selected by the platform manifest, and never
> visible above `hemlock-sai`.

## Schema additions

All are `#[serde(default)]`, so existing manifests parse
byte-identically. `platforms/_template/platform.toml` documents each.

**1. Backend selection — `[sai]`**

```toml
backend = "openbcm"                        # "sai" (default) | "openbcm"
shim_path = "/usr/lib/libhemlockbcm.so.1"  # openbcm only; dlopened by syncd
abi_major = 1                              # openbcm only; refuse a mismatch
```

`package`, `version_pin`, `api_headers` and `libsai_path` become
`Option`, **required by lint when `backend = "sai"`** and rejected when
`backend = "openbcm"`. The section keeps its name: it is the *datapath
library* section, and renaming it would churn every manifest, the
loader, lint, `mkimage.sh` and the architecture doc for no gain.

**2. CPU architecture and ASIC attachment — `[platform]`**

```toml
cpu_arch = "armhf"     # default "amd64"; drives mkimage/installer/verify
asic_attach = "soc"    # "pcie" (default) | "soc"
```

Lint cross-checks `cpu_arch` against the `onie_machine` prefix (`arm-` ↔
`armhf`, `x86_64-` ↔ `amd64`) so they cannot disagree silently, and
requires `asic_attach` when `backend = "openbcm"`.

`asic_attach` replaces the hardcoded PCI probe: `pcie` keeps today's
vendor-`0x14e4` scan, `soc` matches any
`/sys/bus/platform/devices/*.iproc_cmicd` (or a manifest-supplied
name), so no board address lands in Rust. **The `--auto-mock` contract
is unchanged** — absent ASIC → mock with today's warning, present ASIC →
every failure fatal. Only the probe changes, so the QEMU boot test keeps
working on both architectures.

**3. Multiple i2c roots — `[hardware.i2c]`**

The roots here are two **SoC** controllers (`i2c0`, `i2c1`), not one PCI
SMBus adapter: CPLD at `i2c-0` 0x30, pca9548 at `i2c-1` 0x70. Both carry
the same driver name, so `root_adapter` — a single name prefix — cannot
express it.

```toml
[[hardware.i2c.root]]
name = "cpld"                              # referenced as bus = "cpld"
adapter = "Broadcom iProc SMBus adapter"
instance = 0                               # nth match in bus-number order
```

`root_adapter` stays valid as sugar for one root named `root`;
declaring both it and a `[[root]]` named `root` is a lint error.
`I2cDevice.bus`, `Psu.bus` and `Transceiver.bus` become `BusRef`, so
they can name a root; numbers still parse, so the E1031 is unchanged.
Lint: root names unique and non-empty, every `BusRef::Named` resolves.

**4. Runtime bus-number resolution** (its own commit, E1031 first)

Kernel bus numbers for mux children are assigned, not chosen. sysinit
builds a **declared → actual translation table** once at bring-up by
following each mux's `channel-N` symlinks
(`/sys/bus/i2c/devices/<parent>-<addr>/channel-0 → i2c-N`, created by
`i2c-mux.c` for both DT- and `new_device`-instantiated muxes), and every
consumer goes through it: `I2cDevice.bus`, `Psu.bus`,
`Transceiver.bus`; `hw.rs`'s PSU pmbus dir (`{bus}-{addr:04x}`) and
transceiver EEPROM path (`{bus}-0050/eeprom`); and **the `hwmon =
"<bus>-<addr>"` strings** in `[[hardware.thermal.sensor]]` /
`[[hardware.thermal.fan]]` — the E1031 carries `"11-001a"`, `"3-001a"`,
`"23-004d"`, so without those the exercise fixes nothing.

`child_bus_base` stays the **declaration** of which declared number
means which (mux, channel), so manifests do not change and the E1031 is
a no-op today (declared == actual). pmon warns on divergence.

**5. Fan attributes that are not standard hwmon**

ONL's `accton_as4610_fan.c` registers `fan1_speed_rpm` and
`fan1_duty_cycle_percentage`, not `fan1_input` / `pwm1`, and its duty
attribute is **percent**, not 0–255, while Hemlock's sysfs backend
builds `<tach>_input` and writes `percent * 255 / 100`. Three additions
to `[[hardware.thermal.fan]]`, in the style of the existing
`presence_attr` / `led_attr` escape hatches:

```toml
rpm_attr = "fan1_speed_rpm"
pwm_attr = "fan_duty_cycle_percentage"
pwm_max  = 100                             # default 255
```

Absent, behavior is byte-identical to today.

Names alone turned out not to be enough; see 7.

**6. SDK names — `[[ports.group]]` / `[[ports.port]]`**

```toml
sdk_names = ["ge25", "ge24", ...]   # parallel to `lanes`, same length
```

Copied from the porttab's right column. syncd asserts the shim-reported
name for each logical port against this list at startup, so nothing is
derived and a wrong map fails loudly on first boot rather than
mis-cabling someone's rack. Lint checks equal lengths; the mock returns
these names so the assertion is exercised without hardware.

**7. `hwmon` identities that are not i2c clients**

`accton_as4610_fan` registers its hwmon node with *no attributes* and
puts them on the `as4610_fan` **platform** device instead
(`sysfs_create_group(&pdev->dev.kobj, ...)`), so the whole
`/sys/bus/i2c/devices/<bus>-<addr>` shape the `hwmon` field assumes
misses it. The board's other sensor, the `lm77`, is an ordinary i2c
client, so this is a second addressing mode rather than a replacement:

```toml
hwmon = "platform:as4610_fan"       # /sys/devices/platform/as4610_fan
hwmon = "9-0048"                    # /sys/bus/i2c/devices/9-0048
```

One helper (`sysinit::hwmon_device_dir`) turns either into a directory;
`BusMap` leaves the `platform:` form alone, having no bus number to
translate. Lint rejects anything that is neither shape, since both
resolve to paths that simply never exist. PSU presence/power-good needed
the mirror-image fix and no new field: `presence_attr` / `status_attr`
keep their absolute form (the E1031 reads both from its SMC platform
device) but a *bare* name now resolves against the PSU's own resolved i2c
dir, which is where ONL's driver puts `psu_present` / `psu_power_good`.

## The port table

**`lanes` on the OpenBCM backend is the SDK logical port number.** Here
physical == logical (the ICOS `config.bcm` has no `portmap_*` entries);
`bcmd.c` and the `pbmp_xport_*` bitmaps agree that `geN` is logical N+1
(bits 1–49) and `xeN` is logical 50+N (bits 50–55). The `+1` is
documented but never *relied on*, because `sdk_names` carries the names
verbatim and syncd checks them.

- `pbmp_xport_ge = 0x3fffffffffffe` → logical 1..49 = `ge0..ge48`.
  `ge48` (logical 49) is internal (`port_phy_addr_ge48=0`) and omitted;
  syncd logs and ignores unmatched ASIC ports.
- `pbmp_xport_xe = 0xfc000000000000` → logical 50..55: `xe0..xe3` SFP+
  (50..53), `xe4..xe5` QSFP+ stacking (54..55). `bcm56340_4x10=1`.
- Copper MDIO addresses run in six banks of eight with gaps
  (`0x1..0x8`, `0xb..0x12`, `0x15..0x1c`, `0x21..0x28`, `0x2b..0x32`,
  `0x35..0x3c`) — one octal **BCM54282** per bank. SFP+ PHYs are
  `0x40..0x43`.

The faceplate → `geN` map comes from the Cumulus Linux `porttab` for
this platform, reproduced verbatim in the platform README; it is the one
input that cannot be re-fetched from a public repo. I verified the
transcription mechanically: the `lanes` list is exactly porttab + 1 for
all 48 entries, is a full permutation of 1..48, and matches the stated
structure (faceplate 1–24 → `ge24-47`, 25–48 → `ge0-23`, first pair
swapped in every block of four) in all twelve blocks.

The two QSFP+ stacking ports are **not modeled**, as the E1031 omits its
internal ports and Cumulus does not expose them either — which also
removes the `admin_default` field the first draft proposed.

Naming stays `Ethernet1..Ethernet52` and `Management1`; `alias_prefix =
"etp"` matches the E1031, and `swpN` appears only in the README
provenance table.

## Kernel

Upstream has Hurricane 2 but no Helix4, and ONL's 4.14 patch set is the
only public one — so **4.14 is the only known-good iProc kernel that
exists publicly**. systemd's minimum baseline is **5.10** (trixie ships
257.13), so 4.14 cannot boot a Hemlock rootfs at all. Hence: **4.14 is
bench-only** (Phase 3 proves the shim, BDE/KNET and the CPLD sequence
under a minimal init — the Hemlock daemons never run on it); **the real
target is 6.1 LTS, ported directly**, since no intermediate hop is
boot-viable; and **the kernel is on Phase 4's critical path.** Scoped to
what this board's DTS instantiates, the port is ≈4,900 added lines
(≈6,900 with the MDIO/SerDes bucket) out of 29,127 — about 76% of the
patch is dead weight. Full triage, driver-by-driver mapping, the
upstream `brcm,iproc-i2c` compatible collision, and the risk list:
[`as4610-kernel-port.md`](as4610-kernel-port.md).

## Cross-build strategy (Phase 4)

**Rust.** `armv7-unknown-linux-gnueabihf` for the daemons (linker
`arm-linux-gnueabihf-gcc`), `armv7-unknown-linux-musleabihf` for the
installer, which must be static because ONIE has no dynamic loader. Both
tier-2 with std. Preference: link the musl installer with `rust-lld` so
no third toolchain is needed — confirmed in Phase 4, falling back to a
musl cross-gcc otherwise.

**Rootfs.** Debian 13 armhf is a real release architecture (the trixie
`Release` file lists it). `debootstrap --arch=armhf --foreign` +
`qemu-arm-static` + `--second-stage`, then the same package list,
branding, MOTD and initramfs work `mkimage.sh` already does. Needs root
and binfmt, so it stays in `image.yml`'s `full` mode; `--dummy-rootfs`
— what CI runs — needs neither.

**BDE / KNET.** Not from `saibcm-modules` — that is SONiC's SAI-lineage
tree and there is no SAI here. Build OpenBCM's own GPL kernel modules at
`systems/bde/linux/kernel` (BDE) and `systems/linux/kernel/modules`
(`bcm-knet`, `knet-cb`, `bcm-core`, `shared`), driven through
`systems/linux/user/iproc-4_4` with `BUILD_KNET=1`. (The README's
"gpl-module / dcb-gpl-modules" wording is generic across releases;
neither directory exists in `sdk-6.5.16`.) `build/build-bde.sh` is
x86-specific, so Phase 4 parameterizes it or adds
`build/build-bde-arm.sh`.

`[kernel] required_modules` here is **`linux-kernel-bde`,
`linux-user-bde`, `linux-bcm-knet` only.** OpenBCM 6.5.16's `knet-cb.c`
includes only `gmodule.h`, `kcom.h` and `bcm-knet.h` — there is **no
psample**; that is a SONiC saibcm-modules addition, so the E1031's
"psample first — knet-cb's sFlow callback links against it" does not
transfer, and listing it would trip `mkimage.sh`'s modprobe loadability
gate for nothing. Module args: `dmasize=8M` (edgenos's value for this
board) and `default_mtu=9100` for E1031 parity — edgenos's 1600 was to
match their peer network, per their own comment, not a hardware limit.
**Phase 5 validates that against the 4×-smaller DMA pool**: 52 netdevs
of 9238-byte rx buffers against 8 MB.

**Boot artifacts.** No GRUB. A FIT (`boot/hemlock.itb`) via `mkimage
-f`: gzipped kernel `Image` (load/entry `0x61008000`), the board dtb,
and the initramfs — the layout edgenos proved on this box. `mkimage.sh`
selects GRUB vs. FIT from `cpu_arch` and writes an `arch` marker into
the platform overlay.

**Installer.** Hemlock keeps its own self-extracting `.bin` and its own
`hemlock-installer`. edgenos wraps an ONL loader FIT plus a `.swi` with
ONL's python2 `mkshar`; adopting that would import the ONL loader, its
`boot-config` format and a python2 build dependency, and abandon
Hemlock's squashfs + `/hemlock/persist` contract. Instead `install.rs`
grows an ARM strategy that GPT-partitions the USB-attached NOS storage
(a small ext2 partition for the FIT, ext4 for everything else), places
the platform overlay, and sets the U-Boot environment via `fw_setenv`
(which ONIE provides) so `nos_bootcmd` boots the FIT. `machine.rs` stops
defaulting `onie_arch` to `x86_64`. See "Answered on the hardware" for
why this is a block device rather than the NAND an earlier draft
assumed.

**CI stays honest.** `verify-image.sh` reads the payload's `arch` marker
and requires `boot/hemlock.itb` instead of
`grub.cfg`/`vmlinuz`/`initrd.img`, so `mkimage.sh accton-as4610-54
--dummy-rootfs` + `verify-image.sh` still runs on x86 with no toolchain,
no blobs, no root. No CI job needs an ARM toolchain, the OpenBCM tree,
or a blob.

## Definition of done, per phase

**Phase 1 — manifest + mock bring-up (data; x86 CI).** Three commits:
runtime bus-number resolution (addition 4, verified as a no-op on the
E1031); the schema + lint additions; then
`platforms/accton-as4610-54/` with `platform.toml`, `README.md`
(provenance table + raw porttab) and the `image.yml` / CI-lint entries.
Green when build/test/clippy/fmt pass; `platform lint` reports only
vendor-file warnings; `hemlock-syncd --platform accton-as4610-54 --mock`
enumerates `Ethernet1..52` with correct index, speed and media *and*
passes the `sdk_names` assertion; and commit + rollback through mgmtd
works against that mock.

**Phase 2 — `OpenBcmBackend` skeleton (x86 CI, no SDK).**
`openbcm-shim/hemlockbcm.h` committed; `src/hemlock-sai/src/openbcm.rs`
behind an `openbcm` feature; `build.rs` compiles
`openbcm-shim/hemlockbcm_stub.c` into a cdylib in `OUT_DIR` when the
feature is on and exports its path for tests. Implemented:
`create_switch`, `ports` (logical number + SDK name),
admin/speed/duplex/autoneg/mtu, counters, `take_events`,
`capabilities`; the rest return unsupported. `build_backend()` selects
by manifest; `asic_attach` replaces the PCI probe. Green when CI
compiles and clippies `-p hemlock-sai --features openbcm`; tests dlopen
the stub and round-trip every implemented method; an ABI-major
mismatch, a NULL slot and an `sdk_names` mismatch each produce the right
error; and `docs/architecture.md`'s SAI section describes the second
backend and the versioning rule.

**Phase 3 — the C shim (ARM cross container; not CI).** Fetch recipe;
`vendor/openbcm-shim/hemlockbcm.c` + its SDK-tree build script; the
`as4610` quirks impl (`pre_asic_init`: `iproc_cmicd` unbind, the five
CPLD reset-deassert writes read-back verified, char devnodes;
`post_asic_init`: LED program + `led auto on` / `led start`). Runs on
the 4.14 bench kernel (kernel doc, Track 1). Green when the script
produces `libhemlockbcm.so` for `iproc-4_4` with `BUILD_KNET=1` from a
clean checkout, `bcm56340_a0` appears in the built chip table, the quirk
is idempotent, and the bench harness brings a copper port to link
through the shim.

**Phase 4 — armhf image pipeline.** Per-platform arch in `mkimage.sh`;
armhf rootfs; the 6.1 kernel package (critical path); cross-built
BDE/KNET; cross-built workspace; FIT assembly; the ARM install strategy;
`machine.rs` honoring `onie_arch=arm`. Green when `mkimage.sh
accton-as4610-54 --dummy-rootfs` + `verify-image.sh` pass **on x86 in
CI**, and a full build on a Debian host produces a `.bin` ONIE accepts.

**Phase 5 — hardware bring-up.** Console → kernel → management netdev →
BDE/KNET → quirk → `create_switch` → `show interfaces` showing 52 ports
with real link state, **spot-checking the porttab: a cable in faceplate
1 must light `ge25` / `Ethernet1`** → VLAN + PVID → L3 RIF + static
route → OSPF via FRR. Also validates `dmasize=8M` against the chosen
KNET MTU. Findings land in the platform README's "Known quirks", in the
style of `docs/e1031-led-bringup.md`.

**Phase 6 — fill out the backend.** L2 VLANs, FDB, LAG, STP, mirror,
storm control, ACL/policer/CoPP traps, sFlow/samplepacket, QoS — in
that order, plus host interfaces and policers pulled forward out of it
(CoPP attaches policers and punts to a netdev, so neither ACLs nor
sFlow mean anything before those two exist). Landed: L2 VLANs, FDB,
LAG, STP, mirroring, storm control, host interfaces, policers and the
whole ACL family, all of L3, CoPP, sFlow and QoS. **Phase 6 is
complete.** What remains before hardware bring-up is outside the
backend: building the shim inside a real OpenBCM tree (phase 3's
`build-shim.sh`, never run by CI), the 6.1 kernel port, and the board
device tree — the phase 5 gates. Each step: header slots and a minor bump, both shims, Rust
methods, unit tests against the stub, capability flags derived from the
vtable, hardware check.

*Landed: L2 VLANs (ABI 1.2)* — create/remove, tagged and untagged
membership, PVID, the default-VLAN moves, and the QinQ TPID.

*Landed: the MAC table (ABI 1.3)* — aging, static entries both
forwarding and black-hole, flush in all four scopes, per-port learning
and learn limits. Two things worth knowing about it:

- **Flush is one SDK call, not four.** The obvious helpers
  (`bcm_l2_addr_delete_by_vlan`, `..._by_port`, `..._by_vlan_port`) each
  take their own flags, and "static entries survive" is easy to get
  right in some scopes and wrong in others. `bcm_l2_replace` with
  `BCM_L2_REPLACE_DELETE` matches on whatever `MATCH_*` flags are set and
  ignores the rest, so no flags at all means "everything" and
  `MATCH_STATIC` — never set — is what spares static entries, uniformly.
- **No notification path yet.** The slots install and enforce; there is
  no FDB-notification slot, so `SaiEvent::Fdb` and
  `SaiEvent::LearnLimitViolation` never fire on this backend. The shim
  asks the chip to punt over-limit frames to the CPU rather than drop
  them, which is what a later minor needs to turn them into events, but
  the path stops there and the header says so.

*Landed: link aggregation (ABI 1.4)* — trunks, members with the
802.3ad collect/distribute gate, and the LAG-shaped forms of VLAN
membership and PVID. This was the first family where the trait's model
and the hardware's did not line up, and the resolution is worth
recording:

- SAI gives a LAG a bridge port, so a LAG is a VLAN member the same way
  a port is. OpenBCM has no such object — but it does have
  `bcm_vlan_gport_add`, which takes a trunk gport, so the hardware
  models it directly after all. That killed the alternative, which was
  for Hemlock to keep a LAG table and fan VLAN operations out to member
  ports, with all the ordering problems that implies.
- **Members stay in the trunk when the gate is closed.** The obvious
  reading of "not collecting or distributing" is "not in the trunk", and
  it is wrong: ingress classification is a property of the receiving
  port, so a LAG's PVID has to reach every member, and a member the shim
  cannot see is a member it cannot classify. The gate is
  `BCM_TRUNK_MEMBER_{INGRESS,EGRESS}_DISABLE` on a member that is still
  there.
- Member operations go through `bcm_trunk_get` / `bcm_trunk_set` rather
  than `bcm_trunk_member_add` and friends. The incremental calls are
  newer than this SDK's ESW devices and return `BCM_E_UNAVAIL` on some
  of them; get/set is the path every XGS device has always had, and it
  preserves the port-selection criteria instead of guessing at them.

*Landed: spanning tree (ABI 1.5)* — instances as SDK
spanning-tree groups, VLAN-to-instance assignment, and per-instance
forwarding state for both ports and LAGs. Two notes:

- **Assigning a VLAN to an instance is a move.** A VLAN belongs to
  exactly one group, and whether `bcm_stg_vlan_add` relocates it or
  leaves it in both is not documented, so the shim finds the group
  holding it (walking `bcm_stg_list` / `bcm_stg_vlan_list`, since there
  is no reverse lookup) and removes it before adding.
- **Forwarding state is not inherited by a LAG member that joins
  later**, and the ABI says so rather than leaving it implied. The
  reason is structural: a port has a state in *every* instance at once,
  so there is no single value for a joining member to take. PVID is
  inherited precisely because a port has exactly one.

That second point exposed a real bug in the LAG work: the ABI claimed
PVID *was* inherited on join, the stub implemented it, and the real shim
did not — so the test proving it passed against a test double that
was lying about the hardware. The shim now reads the PVID off a member
already in the trunk and applies it to the joiner, which keeps every
member in step inductively and leaves an empty trunk with nothing to
inherit, correctly.

*Landed: port mirroring (ABI 1.6)* — local SPAN sessions and
per-direction port attachment. Two notes:

- The SDK's port-attach call is genuinely additive — a port can feed
  several destinations at once — but the ABI here is a *set*, so
  attaching clears the direction first. Otherwise rewriting a mirror
  would silently accumulate destinations.
- `mirror_sessions_max` is load-bearing rather than decorative: syncd
  refuses a session number above it before anything reaches the
  datapath, so reporting 0 would fail every mirror command up front. The
  SDK has no call that reports the mirror-to-port table depth, so the
  shim states 4 with a comment saying where the number came from and
  that it wants confirming on the hardware. Too low is safe-but-annoying
  (the SDK returns `BCM_E_RESOURCE` when the table fills either way);
  the point is that the assumption is written down where it is made.

Alongside it, a hardening pass the LAG work made necessary. A LAG id is
a `PortId`, so `port.0 as u32` truncates one to its **trunk id** — a
small number that is a perfectly good logical port on this chip. Every
slot that takes a port and only a port now resolves it through a guard
that rejects LAG ids, so `set_port_admin_state(lag)` is an error rather
than a command against whichever port shares the trunk's number. Two
places that had no slot at all for the LAG case — a static FDB entry
pointing at a trunk, and a flush scoped to one — now say so instead of
mis-programming.

*Landed: storm control (ABI 1.7)* — per-port metering of broadcast,
multicast and unknown-unicast, via `bcm_rate_bandwidth_set`. One slot,
and one deliberate absence:

- **There is no per-class drop counter, so the trait's
  `port_storm_drops` reports unsupported.** The chip has a single
  storm-control drop trigger per port
  (`bcmDbgCntRxStormControlDrop`), not one per class. Building an
  answer on it would report the same port-wide number three times as
  though it were three measurements. The header says so at the slot
  that is missing, so the next reader knows it was decided rather than
  forgotten.
- The burst allowance is the one value the caller does not supply and
  the SDK has no default for (0 is a rate, not an absence). An eighth
  of the rate — 125 ms of traffic — is long enough that a rebooting
  rack's ARP burst is metered rather than shredded, short enough that
  the cap still means something, and it changes smoothness rather than
  the enforced rate. Worth revisiting against real traffic.

*Landed: host interfaces (ABI 1.8)* — the CPU punt path and a netdev
per port. Taken out of the stated order deliberately: CoPP traps and
sFlow both punt to the CPU, so neither means anything until packets can
reach a netdev, and without this the box cannot run a control-plane
protocol on a front-panel port at all.

The interesting part is a structural mismatch. SAI models the punt path
as *one* wildcard hostif table entry that delivers each trapped packet
on its ingress port's netdev, plus a NETDEV object per port. KNET has no
wildcard: delivery follows per-filter matches, so "the ingress port's
netdev" is not a rule that can be written once. It is expressed instead
as one ingress-port filter per netdev, installed alongside the netdev.
`host_punt_setup` is therefore `bcm_knet_init` and nothing else — which
is not a no-op dressed up as work, because that init is what clears the
netifs and filters a previous run left in the kernel module, and the
KNET modules outlive the process. It is what makes a syncd restart
idempotent.

Two smaller calls, both flagged where they are made: punted frames have
the internal VLAN tag stripped on the way up (for an access port that
tag was never on the wire, so leaving it would hand the stack a frame
the peer never sent — and tcpdump on the netdev settles it at
bring-up), and a netdev name over the kernel's 15 characters is refused
rather than truncated, since a silently shortened name would collide
with another port's.

*Landed: policers (ABI 1.9)* — single-rate metering in packets or
bits, with conforming and dropped counts. Taken before ACLs and CoPP
because both attach policers rather than define them. Three notes:

- **Rates are split into thousands plus a remainder, not rounded.** The
  SDK carries every rate and burst as a kilo-denominated field with a
  separate 0-999 remainder, and rounding to the nearest thousand would
  turn a CoPP class metered at 100 packets/s into 0. Both halves are
  filled.
- **Colour-blind committed mode.** Nothing upstream marks packets before
  they reach the policer, so treating an arriving packet as any colour
  but green would meter on a colour no one set.
- **The stats mapping is the one unverified thing here, and it is
  labelled as such.** The chip counts colour *transitions*, not
  conformance: green-to-green is what conformed, green-to-red plus
  green-to-drop is what did not, and nothing arrives yellow or red under
  colour-blind mode so the rest of the matrix stays zero. That reading
  is the shim's, no header states it, and the comment says where to look
  if a policer ever reports conforming counts while visibly dropping.

*Landed: ACLs (ABI 1.10)* — tables as field groups, entries with all
ten match fields, the four packet actions, per-port binding and TCAM
utilisation. Not carried yet: match counters and per-entry policers,
which are separate chip objects with their own lifecycles.

- **Groups are created with the full qualifier set, not one tailored per
  table.** A wider qset can cost a wider TCAM slice, but a group's qset
  is fixed at create time and the caller does not say, at create time,
  which fields its entries will use. An entry that cannot be expressed
  is a failure; a slice wider than it needed to be is an inefficiency.
  That is the right way round.
- **Binding is a property of the group.** `bcm_field_group_ports_add`
  exists, so binding does not rewrite entries. Unbinding *without being
  told from what* is the awkward direction: neither side keeps a binding
  table, so the shim sweeps that stage's groups — and only that
  stage's, because taking both would silently disarm an egress ACL
  nobody asked about.
- **Free-TCAM reporting under-counts on purpose.** It sums the free
  entries of the stage's existing groups; space in slices no group has
  claimed is not counted, because the SDK will not say how much of it
  this stage could still take. Under-reporting is the safe direction for
  a utilisation figure.
- **Four things this backend cannot express are refused, not
  approximated.** An IPv6 table (no IPv6 datapath); an IPv6 match in a
  v4 table (truncating to 32 bits would match an unrelated prefix); a
  real L4 port range (the chip needs a range checker, a separately
  allocated resource this ABI does not carry, and matching only the
  lower bound would be a different rule); and an action carrying a
  counter or a policer (installing without them loses the operator's
  `log` or `police` clause while reporting success). An ACL that
  silently matches something other than what was asked for is worse than
  one that fails to install.

*Landed: ACL counters and per-entry policers (ABI 1.11)* — completing
the ACL family, and lifting two of the four refusals the previous unit
had to make.

- **Attachments are set as a unit with the action.** An entry's action
  set is replaced wholesale, and the counter and policer are part of it:
  an update that drops a rule's `log` clause has to detach the counter
  too. One slot takes both, because splitting them would make the order
  between the two calls significant.
- That rule is also where this unit's bug was. The first version skipped
  the attach call when neither object was asked for — meant as an
  optimisation, but "attach nothing" is exactly how a detach is spelled,
  so dropping a `log` clause silently left the old counter attached. The
  test written for that sentence caught it before the commit.
- **A failed attach unwinds the entry.** The attach is a second call
  after the entry installs, and a rule that matches and acts but does
  not count is worse than no rule at all, so a failure removes the
  entry rather than reporting success.
- Counters count packets, not bytes: `show acl` reports matches, and
  asking the chip for both would spend two counter slots to answer one
  question.

*Landed: router interfaces (ABI 1.12)* — port and VLAN router
interfaces and My-MAC entries, the foundation the rest of L3 sits on.
Taken ahead of CoPP because CoPP's most important trap, `Ip2me`, is
"frames addressed to this switch", and there is nothing to address until
a router interface exists.

- **An L3 interface here is per VLAN, not per port.** `bcm_l3_intf_t`
  carries a VLAN id and no port at all, so a SAI port router interface
  has no direct counterpart: it is a VLAN of the port's own, the port
  moved into it untagged, and an interface on that. Four steps that have
  to unwind cleanly, because a port left half-routed forwards nothing
  and looks like a cable fault.
- **The internal VLAN is derived from the logical port, not allocated.**
  `4094 - port`, running down from the top of the 802.1Q space where an
  operator is least likely to have configured anything. That keeps both
  sides free of an allocator — and lets `remove_router_interface` name
  the same VLAN without either side having remembered it. A collision
  with a configured VLAN is loud: creating it returns "already exists"
  and the interface fails, rather than quietly taking over a VLAN that
  is carrying traffic.
- **My-MAC is a separate object from the interface**, because it is
  separate on the hardware and because VRRP virtual MACs need one with
  no interface of their own. The station entry is created for IPv4 and
  ARP together: without ARP the box would answer no resolution for an
  address it routes, which reads as a dead next hop rather than a
  missing flag.
- **No default router MAC.** With no switch MAC resolved, a router
  interface is refused rather than invented: a made-up MAC would come
  up, answer ARP, and put an address on the wire that belongs to
  nothing.

*Landed: routes (ABI 1.13)* — connected subnets, IP2ME punts and null
routes. Deliberately not the two targets that need a next-hop object;
see the open question below.

- **A CPU route is L2TOCPU, not a copy.** These are the switch's own
  addresses, and *routing* one would decrement its TTL and rewrite its
  MACs on the way to a stack that expects neither.
- **Add is a replace.** Retargeting a prefix must not need a delete
  first, or the prefix is unreachable in between. `BCM_L3_REPLACE` on
  every add, and a test that one add after another leaves one route
  rather than two.

*Landed: neighbours and next hops (ABI 1.14)* — and the design
question the previous unit raised turned out to have a better answer
than the one recommended there. That recommendation was a resolution
table in Rust. There is no table.

`bcm_l3_host_find` looks a host entry up by IP and hands back the egress
object it points at — so **the chip's own host table is the resolution
table**. Resolving a neighbour builds the egress object and files it
under the neighbour's address; a route through a next hop names that
address and the shim finds the object. Neither side remembers anything,
and the derive-don't-remember rule survives intact.

That makes a next hop a *name* rather than an object: `create_next_hop`
touches no hardware, creating one twice yields the same id, and removing
one frees nothing. The egress object belongs to the neighbour, which is
where its lifetime actually sits.

- **The egress object's port comes from the FDB.** Nothing the caller
  passes says which port a neighbour is on, so the shim looks its MAC up
  in the interface's VLAN. An unlearned MAC has no port, and a guess
  would be a black hole — so the neighbour does not resolve and the
  route cannot be programmed. That is not a failure mode bolted on: it
  is the resolve-via-punt state the trait already documents, where the
  caller leaves the route pointing at the CPU until the neighbour
  answers an ARP.
- A neighbour behind a LAG gets a trunk egress rather than a port one,
  so hashing still spreads across its members.

*Landed: ECMP groups (ABI 1.15)* — which completes L3. A group is a
multipath egress object and its members are the egress objects the
neighbours own, named by the next hop's address exactly as a
single-path route names one.

- **Groups reserve their width at create time.** `bcm_l3_egress_
  multipath_max_create` takes a path width and an empty member list,
  which is what an empty group needs. Widening later is not an in-place
  operation: the group moves, and every route pointing at it has to be
  rewritten. Reserving one width for every group trades table space for
  never having to do that.
- **An unresolved member is refused.** A group with a hole in it
  black-holes a *share* of the traffic rather than all of it, which is
  harder to notice, not easier.
- The member id carries the group in twenty-four bits and the next hop's
  address in thirty-two, so removing one needs no lookup. Twenty-four,
  not thirty-two: the top byte is the family tag, and this is the second
  time that field width has mattered.

*Landed: CoPP traps (ABI 1.16)* — the family the L3, policer and
host-interface work was pulled forward for. On this chip a protocol trap
is a field entry with copy-to-CPU (plus drop, for a punt) and a policer
attached; the shim owns each kind's match, since several need qualifiers
the generic ACL fields cannot carry (the ARP opcode, "destination IP is
local" for IP2ME).

The forcing constraint was found by reading the caller: `program_copp`
uses `?` on every trap it creates, so one refused kind takes down all of
CoPP at startup. Every kind in the class table therefore has an honest
treatment, and a test pins the full list:

- **The IGMP kinds are indistinguishable on this chip** — the message-
  type qualifier is marked internal-only in the SDK — so all five
  install the same IP-protocol-2 match, per-kind entries so removal
  stays clean. They share one class and one policer in the real table,
  so the imprecision costs nothing there; in different groups, the
  highest kind deterministically wins.
- **MLD installs "IPv6 multicast"** (EtherType 0x86dd, MAC 33:33::/16):
  a superset that genuinely contains MLD, on a box with no IPv6
  datapath to classify deeper. Copies are policed; forwarding is
  untouched.
- **AclLog is accepted and installs nothing.** An ACL entry's CPU copy
  is made by that entry itself, and a second FP stage cannot match "was
  copied by the first" -- so the class exists, its counters read zero,
  and the gap is documented at the trap rather than hidden behind a
  pretend match.
- **IP2ME is `DstIpLocal` at the lowest priority**, so protocol traps
  win overlaps: DHCP addressed to the switch lands in the dhcp class,
  not ip2me.

Statelessness held by leaning on derived ids one more time: the trap
group and its entries use fixed, kind-derived field ids
(`bcm_field_group_create_id` / `bcm_field_entry_create_id`), so a
trap_set is a replace and the default-policer sweep *probes the chip*
for which default-group traps exist instead of keeping a list. The one
exception — the backend's first and only cached word — is the default
trap group's policer: a trap created into the default group later needs
the current value, nothing derivable holds it, and syncd replays the
whole CoPP program after a restart so losing it costs nothing.

A trap group itself is a name for its policer (the id carries it), which
is also why two groups with the same policer are the same group —
harmless, and true to what the hardware can distinguish.

*Landed: ingress sampling / sFlow (ABI 1.17)* — resolving the design
this phase's plan flagged from the start. OpenBCM's knet-cb has no
psample callback, so the E1031's plumbing (psample -> the sFlow engine)
does not exist here. The shim delivers samples itself: a KNET filter
steers packets whose CPU reason is "sample source" into the SDK's RX
API, and the shim's RX handler hands each one to a callback that
becomes a `SaiEvent::SampledPacket` — ingress port and wire length
intact, which the netdev route would have lost.

- **The filter runs at KNET priority 0** — above the per-port punt
  filters — so a sampled copy never goes up the ingress port's
  netdev, where the kernel stack would mistake it for received
  traffic. Priority 0 was left free by the host-interface unit for
  exactly this.
- **The delivery path installs lazily, on the first enabling
  sample_rate_set** — not when the callback is registered at
  create_switch. Found by tracing the restart path: host_punt_setup's
  knet init wipes every KNET filter, and it runs between the two. The
  install is guarded by a file-static flag that dies with the process,
  which is safe for the same reason: the kernel-side filter it tracks
  is wiped by the next run's punt setup before sampling re-enables.
- **A samplepacket session is its rate** — the trap-group shape again:
  one fact, so the id is the fact and nothing is allocated on either
  side.
- **The SamplePacket trap is accepted and satisfied, not refused.** The
  sFlow engine tolerates a refusal but logs "samples will not arrive"
  — which on this backend would be false, since the delivery path is
  installed with sampling itself. Accepting it keeps the log truthful.

*Landed: QoS (ABI 1.18)* — ingress classification maps, default TC,
per-queue scheduling and shaping, the port shaper, WRED/ECN, and real
per-queue counters. **This closes phase 6**: every family in the plan
is implemented or explicitly, documentedly degraded. Still reporting
unsupported, each for a stated reason: per-class storm drop counts (the
chip counts them per port), and the L2MC family — which was never in
the phase-6 plan; IGMP snooping degrades on `l2mc: false` the way it
always has.

*Landed after the close: copper cable diag (ABI 1.19).* One slot over
`bcm_port_cable_diag`, feeding the `show diagnostics cable` front end
the 48 copper ports make worth having. The chip's "open-short" verdict
folds into SHORT — it names a wiring fault, which UNKNOWN (the PHY
declining to classify) does not — and a fibre port answers
unsupported, because a port with no copper PHY genuinely cannot run a
TDR sweep.

This family is where the derive-don't-remember rule honestly ends, and
the ending is worth recording precisely:

- **QoS map objects and WRED profiles are the two places SAI's object
  indirection exceeds what derivation can express.** A map's entry
  table cannot travel in an oid, and `set_wred` edits a profile in
  place on queues that must not be rebound — so the backend must know
  both the contents and the holders. That state lives on the Rust side
  (one map per kind — syncd's own model — plus two small
  binding tables), it is bounded, and syncd replays all of it after a
  restart. The shim stays a stateless "program this port's table to
  exactly this".
- **Scheduler profiles stayed derived**: strict, a 7-bit weight and a
  48-bit kbit/s ceiling fit the id, so syncd's dedup of identical
  profiles costs nothing and `remove` frees nothing.
- **Egress rewrite maps (TC->DSCP, TC->CoS) are not implemented**, and
  degrade cleanly: `qos_map_egress` is false, and syncd's own gate
  refuses those tables with a proper error before the backend is ever
  asked.
- Two smaller honesty points: rate ceilings round *up* to the next
  kbit/s so a small shaper never quietly becomes "unshaped" (0 is that
  encoding), and `wred_queue_stats` stays false because the cosq stat
  set has no WRED-attributed counters — the generic drop counters are
  reported as such rather than relabelled.

*After the close: the shim's first real compile, brought forward.*
build-shim.sh needs the whole SDK built for ARM, so the shim spent
phase 6 as C that had only ever been *read* against the headers — a
caveat its own banner carried. `check-shim.sh` retires most of it: a
headers-only sparse fetch of sdk-6.5.16 plus `gcc -fsyntax-only -Wall
-Wextra`, runnable anywhere, no SDK build, no cross toolchain, and
deliberately not in CI (which must never require the OpenBCM tree).

The first run caught four real defects, which is the argument for the
tool in one sentence:

- **`-DINCLUDE_L3` was missing from build-shim.sh.** Without it the
  SDK's own headers compile the entire L3 API away, and every router
  interface, route, neighbour and ECMP call in the shim would have
  failed on the first hardware build — hundreds of errors deep into
  phase 5, instead of one flag found at a desk.
- `chdir` without `<unistd.h>`, a define used above its definition
  (`HB_ECMP_MAX_PATHS`, consumed by `capabilities()` long before the
  ECMP unit's text), and a signed/unsigned comparison in the sample RX
  handler. All fixed; the file is now diagnostic-free under
  `-Wall -Wextra` against the real headers.

What the check cannot prove is the link and ARM type widths; those
remain for build-shim.sh on the real tree, which is now a much smaller
first step.

Six decisions from these sixteen families set the pattern for whatever
comes after phase 6:

- **Object ids are derived, not remembered.** SAI hands out opaque ids
  for VLANs and memberships; OpenBCM has no such concept. Rather than
  give the shim a table to keep (and to rebuild after a restart), a VLAN
  id *is* its 802.1Q number and a membership id *is* the (vlan, port)
  pair, each under a tag in the high bits so families cannot collide. The
  ids survive a syncd restart with nothing to reload.
- **Idempotency is the caller's job, and is narrow.** The trait documents
  `remove_port_default_vlan` and `restore_port_default_vlan` as
  idempotent. The SDK does not document whether adding a port already in
  a VLAN succeeds or reports it, so the ABI permits either and the Rust
  side accepts both. What it does *not* accept is any other failure —
  which is why `BCM_E_PORT` now maps to INVALID_PARAM rather than
  ITEM_NOT_FOUND: a mistyped port must not arrive wearing the code that
  means "already in the desired state". Nothing in the FDB family is
  documented idempotent, so nothing there is swallowed at all.
- **Optional arguments travel as flags, not sentinels.** `flush_fdb`
  takes a VLAN and a port that are each independently optional, and
  logical port 0 is a real port on this chip — so "no port given"
  cannot be a value. A `flags` word says which arguments count. (The
  stub had made exactly this mistake internally, using port 0 as its
  free-slot marker; the LAG tests caught it, since trunk ids start at 0
  too.)
- **A test that cannot fail is not a test.** The first version of the
  LAG-id guard test used trunk 0, which truncates to logical port 0 —
  a port the stub does not have, so every call in it would have failed
  with or without the guard. It uses the *second* LAG now, whose trunk
  id is 1 and collides with a real port, and it asserts that port 1 was
  left alone. Deleting the guard fails it.
- **A test double that models the hardware wrongly is worse than none.**
  The stub is what every phase-6 test runs against, so a rule it invents
  is a rule the tests will happily confirm. Both times the two shims
  diverged (PVID inheritance, and the stub's use of port 0 as a
  free-slot marker) the divergence was the bug, not the test.
- **Id tags are compared, not masked.** Every derived id carries a
  family tag in its top byte, and the dispatch in `add_vlan_member` and
  `set_port_pvid` turns on it — a LAG id has to be usable wherever a
  port id is. The tags are a numbering, so they are compared for
  equality; `0x03 & 0x04 == 0` is luck, not design.

**sFlow note:** OpenBCM's `knet-cb` has no psample path, so the shim
delivers sampled packets itself (a KNET filter and reason code) rather
than riding the psample plumbing the E1031 uses.

## Answered on the hardware

Captured from the box in ONIE 2016.05 / U-Boot 2012.10, and already
folded into the manifest and the installer:

1. **Console: `ttyS0` @ 115200.** `consoledev=ttyS0`, `baudrate=115200`,
   and `/proc/cmdline` agrees. That is Hemlock's default, so this
   platform needs **no `boot.env`**.
2. **There is no NAND, and no UBI.** `/proc/mtd` holds only the 8 MB
   SPI-NOR (`uboot`, `shmoo`, `uboot-env`, `onie`) and `ubinfo` reports
   zero UBI devices. The NOS storage is a **USB-attached block device
   with GPT partitions** (`onie_partition_type=gpt`) — the stock
   `nos_bootcmd` is `usb start && usbiddev && ext2load usb ${usbdev}:2
   ... && bootm`. The installer's ARM path was rewritten from UBI-on-NAND
   to GPT + ext2 boot + ext4 root accordingly.
3. **`nos_bootcmd` is the hand-off, and it is enough.** `bootcmd` is
   `run boot_diag; run check_boot_reason; run nos_bootcmd; run
   onie_bootcmd` — the NOS command runs *before* ONIE's. This ONIE ships
   **no `onie-nos-mode`**, and does not need one.
4. **Management netdev is `eth0`** in ONIE, `b8:6a:97:3b:8e:40`. The
   manifest's guess was right. Still worth re-checking under Hemlock's
   own kernel, where the name depends on our config rather than ONIE's.
5. **The ONIE machine string uses underscores**:
   `arm-accton_as4610_54-r0`, from `onie_machine=accton_as4610_54` +
   `onie_arch=arm`. The manifest had hyphens — copied from edgenos's
   `switchdb`, which does not match this box — which would have made the
   installer refuse to install onto the very board it was built for.
6. **The i2c controllers are named `iproc-smb0` and `iproc-smb1`**, one
   name each, so they need no `instance` disambiguation. The manifest's
   `iproc-smbus` prefix matched neither.
7. **The mux's channels are buses 10–17**, not the 2–9 the manifest
   declares. `i2cdetect -l` names them `i2c-1-mux (chan_id 0..7)`, so
   this is the first real confirmation that the numbering could not
   have been predicted — which is what the declared→actual `BusMap`
   translation exists for. ONIE cannot *validate* that translation,
   though: its 3.2.69 kernel predates the `channel-N` symlinks
   `BusMap` reads, and creates `/dev/i2c-*` nodes only for buses 0–3.
   Both kernels Hemlock ships do emit the links (verified: `channel-%u`
   in `i2c-mux.ko` on 6.1 and 6.12). The observation did surface a real
   gap — a mux yielding no links used to leave every bus at its
   declared number silently — which `sysinit` now warns about.

8. **The NOS storage is `/dev/sda`, 7.5 GB, GPT, `removable = 0`.** It
   already carries a previous NOS's layout (256 MB + 128 MB + 7.1 GB),
   which the install zaps. Despite U-Boot reaching it through `usb
   start`, the kernel does not flag it removable — so the installer's
   existing "never offer a removable device" filter is right on both
   boot styles, and a draft exception for FIT boards was removed.
9. **ONIE lives in SPI-NOR (`mtd3`), not on `sda`.** U-Boot boots it
   straight out of flash, so a bad install on `sda` cannot brick the
   box: ONIE is always reachable and the install is never one-shot.

10. **The PSU bays are at 0x50/0x51 on mux channel 6**, as edgenos's
    device tree says, with their pmbus devices at 0x58/0x59. ONL's PSU
    driver disagreed (0x50/0x53) but its address list was dead code, and
    the local port drops it. Not modeled: the pmbus devices, since pmon's
    per-PSU reading is presence and power-good, both of which come from
    the CPLD.
11. **This chassis is an AS4610-54T revision B** — CPLD register
    0x01 reads `0x05` (`PID_AS4610_54T_B`). It therefore **has fans**,
    which a plain 54T does not, so the manifest carries two fan
    entries and a curve. Nothing on the outside of the box
    distinguishes the two revisions.

## Open questions

1. **Does this U-Boot's `ext2load` read ext4?** Unknown, which is why
   the FIT sits on a small ext2 partition of its own. If it does, the
   layout could collapse to one partition; not worth the risk until
   someone types `ext2load` at the U-Boot prompt.
2. **In-band upgrade across the two-partition split.** `hemlock_common::image`
   replaces `rootfs.squashfs` *and* the boot assets on the flash the
   initramfs mounts at `/host`. On this board the FIT lives on a
   *separate* ext2 partition, so an `upgrade` would refresh the rootfs
   and leave the old kernel in place. Not a bring-up blocker — reinstall
   from ONIE works, and ONIE cannot be lost — but the upgrade path needs
   either the boot partition mounted under `/host` or an arch-aware
   branch in the image engine before `upgrade` is trustworthy here.
3. **Is `i2c-mux-idle-disconnect` required?** DT/platform-data only, so
   it cannot be set through `new_device`. If it proves necessary — it
   may be implicated in the RTC-related i2c wedge — the fallback is
   keeping the *mux* in the DTS but not its children.

The kernel document's own open questions have moved: mainline 6.1
turned out to carry the whole SoC family (see its "Mainline 6.1
already carries the SoC" section), so the edgenos-tree question is
answered "unnecessary" and the remaining kernel unknowns are the
USB nodes, the SMP boot register, and whether the management link
comes up on mainline bgmac + iproc-mdio alone.
